# K3.2a / K3.2c handoff: GPU coarse pyramid, `hdda` on, hardware timings

On the worktree branch from `v2` (e5353ab), per D29. Status: K3.2a ✅ (functional and parity gates); K3.2c 🟨 (harness
done and run once on the hardware GPU, but **provisional**: another agent was running reference captures in a
separate Chrome on the same GPU, load average ~6–8 on 18 CPUs). The hdda default is on as D29 asks; the numbers
below argue for turning it off (see Recommendation).

## What exists

| Piece | Where | What it does |
|---|---|---|
| GPU pyramid (core) | `packages/vdb/src/core/compute/pyramid.ts` `createBoxPyramid(device, pool, id, { indexBox, pyramidMax, level, targets })` → `VDBBoxPyramidGpu` (`record(encoder, { timestampWrites })`, `update(encoder)`, `stale`, `builtRevision`, `gpuBytes`, `destroy()`); `boxPyramidWgsl(type)` | Engine-free. One compute pass recorded into the host's encoder, slot-mode `march` module at `COMPUTE_SLOT` (group 0 = pool + a dynamic-offset uniform, group 1 = scratch). Passes: **base** (one thread per texel: `resampleGrid`'s area-weighted box filter over the index cell box, overlaps as exact integers in 1/D-voxel units, summed x→y→z like the CPU; an empty-space fast path when every 8³ cell under the footprint is an inactive zero tile), **mask** (texels of 8³ blocks with no active tap → 0, the CPU drops those leaves), **levels** (his 2x2x2 clamped box mips into his atlas layout, from f32), **pack** (f32 → f16 with three's `toHalfFloat` table: truncation) + `copyBufferToTexture`. Owns its scratch buffers and, without `targets`, its r16float textures; never the host's. |
| Shared layout | `packages/vdb/src/tools/frame/pyramid-layout.ts` `vdbBoxPyramidLayout`, `vdbPyramidLevelSize` (and `vdbPyramidBaseLevel` moved here) | The sizes/offsets both builds use; `vdbBoxPyramid` now reads it. |
| Pool | `VDBGridInfo.imageRevision` (`core/pool/pool.ts`) | The pool `revision` at the grid's last `add`/`replace` (not `setTransform`/`setMajorant`; a reused id gets a new one). What "rebuild on change for that grid" keys on. |
| three | `vdbSparseSource` option `pyramidBuild: 'gpu' \| 'cpu'` (default `'gpu'`), `pyramid.gpu`, `pyramidBuilds`, `refreshPyramid()`, `gpuBytes.pyramidScratch`, type `VDBSparsePyramid` | GPU path: `Data3DTexture(null, …)` with `source.dataReady = false`, `renderer.initTexture`, then the core writes three's own `GPUTexture`s (`targets`). The first build happens at creation if the grid is resident; afterwards the `pyramidLevel` uniform's `onRenderUpdate` calls `refreshPyramid()` (cheap: compares `pool.revision` first) and rebuilds when the density grid's `imageRevision` moved: sequence frames work. `images.density` is no longer needed for the pyramid (only for stats, unless `stats` is passed). `'cpu'` keeps the K3.2 path (static) as the twin. The source's `version` now follows the channel grids' `imageRevision`, so `'frame'` lighting's caster signature (V44) redraws the shadow grid after a `pool.replace`. |
| HDDA default | `packages/vdb/src/three/frame/volume.ts` (`hdda = true`, the default line and its doc comment only) | D29. Images unchanged (K3.2: identical to ≤ 1/255); all K3 specs and goldens unchanged. |
| Parity harness + e2e | `examples/src/harness/k3-pyramid.{html,ts}`, `e2e/k3-pyramid.spec.ts` | Reads the GPU textures back and compares with `vdbBoxPyramid` + `toHalfFloat` texel by texel (f16 ulp distance); sequence replace; three source GPU vs CPU textures, rebuild count across renders, `version` bump. |
| Timing harness | `examples/src/harness/k3-timing.{html,ts}`, `examples/src/harness/k3-pass-timer.ts`, `scripts/k3/time-hardware.mjs` | One configuration per page load; per-pass GPU ms from three's render-pass timestamps mapped to `passHook` names (uids made unique; see CLAUDE.md trap), integrate and scene by difference, a queue-synchronised whole frame (render → `onSubmittedWorkDone`) and a throughput figure. The script launches installed Chrome headed (`channel: 'chrome'`, `--enable-webgpu-developer-features` for unquantized timestamps), refuses SwiftShader/fallback adapters, prints the adapter, records load average and the busiest processes, labels results provisional unless `--quiet`, writes `artifacts/k3/hardware/timings-<stamp>.{json,md}`. `--only=hdda,gap,k3frame,pyramid`, `--small --allow-swiftshader` to debug the script. |

## Hardware timings (K3.2c) — PROVISIONAL

Apple M5 Pro (`apple metal-3`), Chrome 157.0.8103.80, `timestamp-query` on. Another agent's reference captures were
running in a separate Chrome on the same GPU; load average 7.9 → 5.9. 1920x1080, froxels 512x512x24, 32 sub-steps,
32 shadow steps, medians of 30 frames after 10 warm-up; ms. Full output: `artifacts/k3/hardware/timings-latest.{json,md}`

HDDA costs more than it saves in all 12 cases on the hardware GPU too: 1.07–3.31× the inject pass (median ~1.9×),
+1 to +46 ms per 1080p frame. The default `'coarse-pyramid'` pays the most (2–3.3× on the clouds). The walk is
divergent per froxel and runs 8 node lookups per 8³ cell, while the samples it skips are cheap (one r16f texture
fetch at coarse lods). It comes closest to break-even on the sparsest asset (WDAS + pyramid, 1.07×).

K3.3 timing scene (`step3-default-dir-isolated`, his bunny, k3-frame's own timing, 1080p): froxels dense 0.46 ms vs
sparse 2.06 ms (**4.5×**; SwiftShader was 51.6 vs 292.6 ms, 5.7×); grid redraw 1.18 vs 1.37 ms.

- **'frame' lighting: the density pass dominates** (the only froxel pass that samples the source: 5.3–15.5 ms sparse
  vs ~0.9 ms dense). The "lighting" pass shows the same ms as density in every sparse run, but it is source-free
  (`lighting-material.ts`) and costs ~0.8 ms on dense: on Apple's tiler its begin timestamp lands while the density
  pass is still running, so the per-pass sum double counts. Use the frame wall time for the total (3.9–10.7×) and
  the density pass for the cost centre. The shadow-grid redraw is cheap (shadow density 0.02 ms, transmittance
  0.5 ms) and cached in a still scene.
- **'volume' lighting: the inject pass is 14–23× dense** with HDDA on; with it off (table 1) sparse-pyramid is 6–18 ms vs
  ~1 ms dense (8–21×). The 32 shadow steps × 32 sub-steps per froxel each do an 8-tap sparse trilinear at level 0
  near the camera, where dense does one hardware-filtered 8-bit fetch.
- Run-to-run noise under the concurrent load: cloud04 'volume' sparse-pyramid-hdda measured 12.6 ms in group (1)
  and 20.3 ms in group (2), same configuration. Treat single figures as ±50%; the ratios within a group are paired
  minutes apart.

GPU memory: the textures are the same r16f bytes as the CPU path (2 B per base + atlas texel). The scratch (f32 base
and atlas, block flags, the 256-byte-row f16 staging, parameter slots) stays allocated for rebuilds (a sequence
replaces the grid every frame): ~3.7–4.8× the texture bytes. A rebuild per sequence frame costs ~4 ms on WDAS,
~0.2–0.5 ms on the 128³-class clouds. SwiftShader for scale: WDAS 300 ms GPU vs 412 ms CPU.

## Recommendation on `hdda` (D29)

**Turn it off.** D29 keeps it on unless the measured cost is large; on the hardware GPU it is: never a gain in 12
paired runs, and with the default `'coarse-pyramid'` LOD 2.1–3.3× the shadow-march pass (+7 to +26 ms per 1080p
frame) on the three clouds; WDAS is the only near-tie (1.07×, +1 ms). The images are identical either way, so turning it off only changes speed. This
branch makes it the default as instructed (one line in `frame/volume.ts`); flipping back is that line. Caveat: the
run is provisional (concurrent GPU load); a `--quiet` rerun should confirm the direction, but a 2–3× paired gap is
unlikely to reverse. Worth keeping the code: a cheaper walk (a coarser bound, e.g. lower-node 128³ cells, or a
per-froxel early-out on the pyramid's coarse level) might pay later; that is a new A/B, not this default.
