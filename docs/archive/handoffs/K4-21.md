# K4.20 (remainder) and K4.21 handoff

## K4.20: stream progress, typed `NanoVDBFile` errors

### Progress (tools `nvdb-stream.ts`, three `coarse-first.ts`)

- `NvdbStreamReader` exposes `bytesReceived` (existing), `bytesTotal` (`number | null`) and `progress`
  (`{ bytesReceived, bytesTotal, gridsEmitted }`). Options: `bytesTotal` (a caller-known size, wins) and
  `onProgress(progress)`, called after every non-empty `push` (outside the push's error handling).
- Without the option, `bytesTotal` is derived from the file: once the last FileMetaData + name of a segment has
  arrived, the segment ends at `start + 16 + sum(176 + nameSize + FileMetaData.fileSize)`. `fileSize` is the on-disk
  size including codec framing, so this is exact for ZIP and NONE (tested on both). It is null before the first
  segment's metadata is in, exact for a one-segment file, and the end of the latest segment seen (a lower bound)
  when more segments follow. `ParsedFileMetaData` gained `fileSize`.
- `NvdbStreamGrid.bytesTotal` rides on every grid event; `VDBCoarseFirstEvent.bytesTotal`,
  `VDBCoarseFirstResult.bytesTotal` and `VDBCoarseFirstOptions.onProgress` carry it through `vdbStreamCoarseFirst`.
- `nvdbResponseLength(response)`: the Content-Length, or null when absent, malformed, or when a Content-Encoding
  other than identity is set (the decoded bytes the reader counts then differ from the header). `readNvdbStream` now
  accepts a `Response` (uses it for `bytesTotal`), as `vdbStreamCoarseFirst` already did.
- Demo 09 drives its counter's total from the reader (`onProgress`); its golden is unchanged (the demo's throttled
  Response has no Content-Length, so the total comes from the metadata). `e2e/demo-09.spec.ts` asserts the reader's
  total equals the file size (`state.streamTotalBytes`).

### Errors

- `NvdbFormatError` moved into `nvdb-file.ts` (still exported from `tools` and `nvdb-stream.ts`). `NanoVDBFile`
  and its helpers throw it for malformed or truncated input: truncated buffer, bad magic, version mismatch, bad
  codec value, ZIP inflate failure and size mismatches, GridData size mismatches, non-segment trailing bytes.
  `instanceof VdbFormatError` holds.
- `VdbUnsupportedError` for valid data out of scope: the BLOSC codec and unsupported grid types
  (`validateGridType`). The stream reader already mapped these two; it now passes them through unchanged.
- Messages are unchanged apart from the class prefix (`@pmndrs/vdb/tools: malformed .nvdb: NanoVDBFile: ...`), which
  the stream reader's errors already carried; every existing `toThrowError(/.../)` test still matches. Left as plain
  `Error`: `fromURL`'s HTTP failure and the out-of-range grid index (not format problems).
- Tests: `nvdb-file.test.ts` (class, name and prefix for garbage and short buffers, BLOSC unsupported, unrepresentable
  gridSize), `nvdb-stream.test.ts` (progress for NONE and ZIP, multi-segment, `bytesTotal` option, `nvdbResponseLength`,
  `readNvdbStream(Response)`).

## K4.21: `.wvdb` bake sampling A/B

Image metric only; no timings (D25). Headless Chromium on SwiftShader, 224x224, 192 march steps, two poses (demo 02's).
Reproduce:

    PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=... WEBVDB_E2E_PORT=5427 WEBVDB_WRITE_K421=1 npx playwright test e2e/wvdb-sampling.spec.ts
    # WEBVDB_K421_EXT=100 -> K4-21-ext100.json; WEBVDB_K421_RES=128,64; WEBVDB_K421_VOLUMES=smoke,bunny_cloud,wdas

Harness `examples/src/harness/wvdb-sampling.{html,ts}`; full rows in `K4-21.json` (extinction 20) and
`K4-21-ext100.json` (his FrameVolume default, near-opaque).

### Method

- Volumes: `smoke.vdb`, `bunny_cloud.vdb` (float `density`), and the WDAS quarter cloud (the Fp8 `.nvdb`, via
  `nanoVdbToWvdb`; the 68 MB `.vdb` is not needed).
- Bakes (in the page): `nanoVdbToWvdb(image, { resolution, sampling })`, `resolution` 128 (his default) and 64,
  `sampling` `'nearest'` and `'box'`, default 3 LODs, 8 bits. Each file is read back (`readWvdb`) and drawn through
  the K3.0 dense source: `wvdbDenseVolume({ mipmaps: false })` -> `vdbDenseTextures` -> `vdbVolumeNodes`, texels
  `clamp01`, the k3-dense harness's emission-absorption march, `normalizeDensity: false`.
- Reference ("ea", primary): the SAME march over the same box, density read from the full-resolution sparse grid in a
  `VDBGridPool` with `vdbSample` (trilinear) clamped to [0, 1] as the texels are. Using one march for both sides keeps
  lighting and step model out of the comparison; only resolution, filter and 8-bit quantisation differ.
- Reference ("vvm", as asked): the sparse grid drawn by `VDBVolumeMaterial` (densityScale 4 / 4 / 40). It is a
  different renderer (lit, shadow-marched, per-voxel steps), so every bake sits at 17 to 22 dB from it whatever its
  sampling (differences between samplings: < 0.2 dB, no ranking value). Reported in the JSON only.
- Metrics: `scripts/k3/metrics.mjs` `psnr` and `above(.., 8)`, plus signed mean luminance bias (bake - reference).

### Findings

1. It is a wash on the image: at extinction 20 |box - nearest| <= 0.54 dB at 128 and <= 0.96 dB at 64 (<= 1.5 dB at extinction 100), and the sign flips with the
   resolution and the optical depth. Box leads by 0.4 dB at 128 / extinction 20 and trails by 0.3 to 1.0 dB at 64 and
   at extinction 100. Resolution matters far more (128 vs 64 is 5 to 6 dB for either sampling).
2. Box files are 7% (smoke 128) to 24% (bunny 64) larger: averaging smears the support, so more bricks are non-zero.
3. Box renders slightly brighter (bias +0.03 to +0.12 vs nearest at 64): the same smeared-coverage effect as K4.19
   (box fattens the silhouette). It conserves mass, which the image metric does not reward.
4. Nearest is his CLI's sampling, and `'nearest'` reproduces his committed files byte for byte (K4.13, V17). Switching
   the default would make `vdbToWvdb(x)` differ from his `wvdb` CLI on the same input.
5. Caveat: the reference is the sparse grid's trilinear sample, and the baked sources here are only moderately finer than
   128 texels (the source-to-texel ratio was not recorded). A much finer source (a full-resolution WDAS, EmberGen frames at 1024+)
   is where nearest aliases and box should pull ahead; not measured. His `normalizeDensity` (mean of non-zero texels)
   also interacts with the sampling's mass; not measured (the A/B fixes the density scale).

### Decision proposal (D27, for the owner; DECISIONS.md not edited)

> **Keep `sampling: 'nearest'` as the `.wvdb` bake default; keep `'box'` as an opt-in.** On smoke, bunny_cloud and the
> WDAS quarter cloud, rendered through the dense source against the same march over the full-resolution sparse grid,
> box and nearest are within 0.5 dB at his default resolution (128) and within 1 dB at 64, with the sign depending on
> the resolution and the optical depth; box files are 7 to 24% larger and render slightly brighter. Nearest matches
> his CLI byte for byte (V17), so it stays the default for parity. Recommend `'box'` in the docs for sources much finer
> than the texel grid (aliasing) and for baked mass that is read quantitatively. Revisit with a high-resolution source
> (full WDAS, EmberGen) and a hardware GPU; this run is SwiftShader (full-float `r8unorm` filtering).

Not changed: the default in `bake.ts`.
