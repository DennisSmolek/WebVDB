# K4.3 handoff: `.wvdb` read and write in `@pmndrs/vdb/tools`

mjurczyk's WebVDB format (spec `src/docs/wvdb/README.md`, "Version 0.5.x", file versions 1 and 2 incl. points
grids) is read and written by pure TypeScript in `tools` (Node and browser, no `node:` imports, zlib via
`fflate`). Source of truth: mjurczyk/openvdb at `75e7345` (v0.26.0), read only. Ported logic carries the header
"Portions derived from mjurczyk/openvdb (MIT), commit 75e7345".

## What exists

| File (`packages/vdb/src/tools/wvdb/`) | Contents |
|---|---|
| `format.ts` | Constants, header types, brick math (§3.3), page/mask/points chunk encode + decode with exact size checks (§6, §7, App. B). Derived from his `format.js` |
| `read.ts` | `readWvdbHeader` (§4/§5/§14 validation, `null` while incomplete), `wvdbChunks` (§9 order), `wvdbLodByteRange` / `wvdbPrefixLength`, `decodeWvdbLod` (from a whole file, prefix, or one range read), `readWvdb` (whole file or `partial` prefix), `WvdbStreamReader` (push bytes, get LODs coarse first), `inflateWvdbChunk` (bounded inflate) |
| `write.ts` | `writeWvdb` (volume grids from the finest LOD or all LODs; points grids from positions/colours), `downsampleWvdbLevel`, `wvdbDensityStats`, `wvdbPointLods`. Derived from his `bake.js` / `writeWVDBFile` |
| `bake.ts` | `bakeWvdb` over `WvdbSampleSource`s; `wvdbSourceFromVdbGrid` (parsed `.vdb`), `wvdbSourceFromNanoVdb` (NanoVDB image via the CPU oracle `readValue`); `vdbToWvdb` (his CLI, from bytes or a `VdbFile`), `nanoVdbToWvdb`; `wvdbFinestDimensions`, `sampleWvdbDense`. Derived from his `bake.js` / `cli.js` |
| `sha256.ts` | Synchronous SHA-256 for `source.sha256` |

All exported from `tools/index.ts` (chunk codecs renamed `encodeWvdbPage`, `decodeWvdbMask`, …).

Decoded volume LODs are dense `Float32Array`s, channel planes one after the other, x fastest, background where
a sparse LOD stores no brick; each level also keeps `brickIndices` (file order), `mins`/`maxs` and the mask.
Points LODs are per-LOD `positions`/`colors` with `firstPoint`. This is the `WVDBLevels` input R1 §4.2 names for
`vdbDenseSource` (K3.0).

Writer defaults are his CLI's: 3 LODs, 8 bits (16 optional), sparse, 1024 bricks per page, 2^18 points per points
chunk, constant brick channels store no codes, all-background bricks are dropped in sparse layout, bricks with
the most data first, coarse-to-fine chunk order, `meanDensity`/`nonZeroVoxels` for scalar grids, his header key
order. Compression defaults to fflate `zlibSync(level 9)`; pass `compress` (e.g. Node `deflateSync`) to choose.

The baker is his point sampling, no prefilter (the only mode, `sampling: "nearest"`): voxel centre → inverse map →
`Math.round` → value lookup. A source much finer than the target aliases, as in his CLI.

## Verified against his files

All eight of his files I tried decode with `strictChunkOrder` (§9: coarse to fine, grid order, no gaps, ends at
EOF): `ground_explosion_0010`, `ground_explosion_0199` (empty frame), `cloud_04_variant_0000` (committed), and
`venusstatue`, `utahteapot` (level sets), `sphere_points` (v2), `smoke`, `bunny_cloud` (via env).

- **Header fields**: magic, versions (1, and 2 for points), `brickDim` 8, `bake`, `source`, per-grid members,
  every chunk inside the data section. `source.sha256` equals the SHA-256 of the source `.vdb` for smoke,
  bunny_cloud, venusstatue, utahteapot and sphere_points (his checkout), and our own pinned `smoke.vdb` manifest.
- **LOD dims**: coarser = `ceil(finer / 2)` everywhere. Finest = §3.2.1 from the box for cloud_04, venus and
  teapot. Ground explosion, smoke and bunny_cloud are `128³` (baked before his cube-texel fix).
- **Brick bitmasks**: mask popcount = `bricks`; mask set = page indices; no bits past `brickTotal`; each inflated
  page has exactly the Appendix B size; brick placement checked against a hand decode of raw page bytes using the
  §3.3 formula.
- **Decoded values, cross-checked with his metadata**: `nonZeroVoxels` and `meanDensity` recomputed from our
  decoded finest LOD equal his header **exactly** (integer count and float mean) for every file with stats
  (ground explosion density 31,468 / flames 33,212, smoke 570,069, bunny 275,039, venus 16,822, teapot 28,522).
  Level-set values outside the band are exactly ±b. sphere_points: 9,802 points, LODs 154/1,072/8,576, all
  inside the box and at radius ≈ 1.
- **Re-encode, his brick order** (`brickOrder: level.brickIndices`): the header (offsets zeroed) and **every
  inflated chunk are byte-identical** to his, for all eight files, points included.
- **Re-encode, our default order, Node zlib 9**: decoded content identical. **Whole-file bytes are not
  identical**, for two reasons: (1) bricks with nearly equal weight can swap order, because weights are taken
  from decoded rather than source values; (2) zlib: re-deflating *his own* inflated chunks with this machine's
  Node 22.22.2 zlib (`1.3.1-e00f703`, Chromium's fork) at level 9 reproduces only some of his chunks (3 of 12 for
  ground_explosion_0010, 0 of 8 for smoke), so his files came from a different zlib build. So the claim is
  "identical inflated chunks and decoded content", not identical bytes.
- **Full pipeline from source**: `vdbToWvdb(smoke.vdb, { dimensions: [128,128,128] })` (our `.vdb` parser →
  his point sampling → box-filter LODs → quantize → pages) reproduces his `smoke.wvdb`: same header apart from the
  stats (see ambiguity 3), and all 8 inflated chunks have the same SHA-256. The NanoVDB path
  (`buildFromVdb` → `nanoVdbToWvdb`) produces the same bytes as the `.vdb` path.

## Spec ambiguities (and what we did)

1. **Version naming.** The spec is "0.5.x"; the file `version` is 1 or 2. Reader accepts 1 and 2; writer writes 1
   without points and 2 with (§11).
2. **§3.2.1 is a SHOULD.** Three of his committed files use `resolution³` instead of cube texels. Readers must
   take `dimensions` from each LOD, never from `bake.resolution`. `bakeWvdb` has a `dimensions` override to
   reproduce such files.
3. **`meanDensity` / `nonZeroVoxels` source.** §5.4 says the 8-bit density of the finest LOD, without saying
   before or after quantization. His committed headers match the *decoded* data (they were added later from the
   existing files, per his CHANGELOG); his current writer uses the *pre-quantization* values. A fresh bake of
   smoke gives 570,010 non-zero voxels vs 570,069 in his file. We compute from the values given to the writer,
   like his current writer.
4. **Level sets.** §8 is defined by source *active* state (inactive → ±b by sign; active → clamp to ±a). His CLI
   samples level sets with `sampleLevelSet` (a surface-aware mean, not §3.2.2 point sampling) and clamps any
   `|v| < b` regardless of active state. We follow the spec text, so level-set *bake* output differs from his CLI
   (decode and re-encode are unaffected).
5. **Edge replication (§3.3)** "nearest voxel inside the LOD on the same brick axis" is unclear at corners; his
   code clamps each axis independently. We do the same.
6. **Signed zero and NaN.** The spec does not say whether min/max treat −0 < 0, nor what a NaN value or colour
   encodes as. We follow his code: `Math.min/max`, NaN samples → background, NaN colour → 1.0.
7. **Optional members his loader needs.** `channels` (default 1) and `spacing` (optional) — his
   `WVDBLoader` computes point size from `spacing` without a guard. Our writer always writes both (`spacing`
   estimated as `cbrt(boxVolume / sourceCount) · cbrt(stride)` when not given; his CLI derives it from voxel
   size).
8. **`source` without a source file.** `sha256` is required (64 hex). `writeWvdb` from arrays defaults to
   `{ file: "", sha256: 64 zeros }`; `vdbToWvdb` from bytes hashes them.
9. **Reader strictness.** §14 asks readers to reject wrong sizes, out-of-range indices and out-of-bounds chunks;
   his reader checks none of these (nor `brickCount`, nor that mask and indices agree). Ours checks all, so a
   malformed file his reader tolerates is rejected here. None of his files trips it.

   `VDBPoints`.

   `vdbToWvdb(bytes, { fileName: "smoke.vdb", compress: (b) => zlib.deflateSync(b, { level: 9 }) })` under the
   *same* Node; bytes should match exactly if the zlib builds match. Level-set sources will differ (ambiguity 4).
