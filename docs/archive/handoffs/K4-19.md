# K4.19 handoff: coarse-first preview filter A/B (box vs point vs trilinear)

Image metric only; timings wait for a quiet machine (D25). Headless Chromium on SwiftShader (`google swiftshader`),
224×224, jitter off, VDBVolumeMaterial defaults (12 shadow steps). Reproduce:

    PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH=... WEBVDB_E2E_PORT=5419 WEBVDB_WRITE_K419=1 npx playwright test e2e/preview-filter.spec.ts
    # WEBVDB_K419_RES=24|96 changes the preview resolution; WEBVDB_K419_VOLUMES=smoke,wdas,explosion,fire adds samples

Harness `examples/src/harness/preview-filter.{html,ts}`, spec `e2e/preview-filter.spec.ts` (~10 s), full table in
`docs/handoffs/K4-19.json` (24 rows: volume × filter × {aligned, shifted} × 2 poses). The spec has no ranking gate;
it asserts the frames are non-empty and PSNR > 12 dB so a broken render fails.

## Method

- Volumes: `smoke.vdb` (density, FLOAT image; full density scale 4) and the WDAS quarter cloud
  (`wdas_cloud_quarter_fp8.nvdb`, the Fp8 bake, used as both the full grid and the preview source; density 40).
- Previews: `resampleGrid(source, { resolution: 48, filter, quantize: 'fpn' })` on the source's active cell box
  ("aligned": 24×48×25 smoke, 39×27×48 WDAS), and the same lattice shifted by half a preview voxel on every axis
  ("shifted": `bbox` + `dimensions` of the aligned result). Drawn with `densityScale × voxelRatio` (K4.16): ratio
  4.63 on smoke, 12.77 on WDAS.
- Reference: the full grid at `densityScale`, same camera, demo 02's two test poses (az/el/radius = 0.25π/0.16π/1.7
  and 0.85π/0.34π/2.0 diagonals, 45° fov).
- Metrics: `scripts/k3/metrics.mjs` `psnr` and `above(.., 8)` (% of pixels with max channel diff > 8/255); plus the
  signed mean luminance bias (preview − full, 8-bit units; > 0 = preview brighter).

## Findings

1. Differences are small. Everything lands within ~1.1 dB, and a 48-voxel preview is 28 to 38 dB from the full
   render whichever filter made it; the voxel ratio (the coarse silhouette), not the filter, is the main error.
2. Trilinear and point beat box on pointwise image error in every volume and at every resolution tried:
   +1.07 dB (trilinear) and +0.98 dB (point) over box at 48; +1.2 / +1.2 at 24; +0.5 / +0.3 at 96. Trilinear ≈ point
   (≤ 0.2 dB apart, trilinear ahead on smoke, point ahead on WDAS). This matches K4.4's pointwise finding
   (smoke 128³: 17.3% vs 18.3%).
3. Box is the most stable under a half-voxel shift (swing 0.08 vs 0.18 / 0.17 on smoke + WDAS; on fire 0.33 vs
   0.64 / 0.77). The swings are small (< 0.8 dB, none visible as flicker at these ratios), so the aliasing worry
   is real but minor on these volumes. Fire (sharp flame structure) is the case where it shows.
4. Box conserves mass (the K4.4 argument) but renders a brighter, fatter preview than the reference on WDAS
   (+1.34 vs +0.83 / +0.88): coverage grows because the exponential transmittance of a smeared layer is more opaque
   than the thin core it came from. Mass conservation does not buy a closer image.
5. Cost: box previews have more active voxels (smoke 14.4k vs 10.6k point / 11.9k trilinear; image bytes within
   ±0.4%), so no meaningful size difference after FpN.

## Decision proposal (D26, for the owner; DECISIONS changes after approval)

**Make `'trilinear'` the default `bakeCoarseFirst` preview filter** (was `'box'`), keep `'box'` and `'point'` as
options.

- Why: best mean PSNR over smoke + WDAS at 24, 48 and 96 (30.40, 33.94, 37.06), and best on smoke at 48 and 96.
  On WDAS point is marginally ahead (29.53 vs 29.48 at 48; 27.10 vs 26.94 at 24; 31.61 vs 31.59 at 96), so the
  trilinear/point choice is a tie on image error; trilinear is smoother. Lowest % > 8 on smoke, tied with point
  on WDAS; no extra cost.
- Pros: smoother than point (no nearest-voxel blockiness when the preview is magnified), no sampling-phase
  jumps on smooth fog, cheapest to explain ("sample the field at the preview voxel centre").
- Cons: it is point-sampling plus a 2×2×2 blend, so at large ratios (≥ 8) thin features can miss samples and flicker
  with the lattice phase more than box (fire: 0.77 vs 0.33 dB swing); box stays the right choice for thin or
  high-frequency data and for anything that reads the preview quantitatively (mass).
- The test that would settle it further: the same table on EmberGen frames and a thin-structure volume (smoke plume
  lit at grazing angles), plus a hardware GPU run (`float32-filterable` and 8-bit texture weights differ from
  SwiftShader; this harness does not exercise either, it samples the NanoVDB). Timings are deferred (D25).
- If the owner wants zero risk for high-frequency data: keep `'box'` as the default and document `'trilinear'` as
  the pointwise-best option; the evidence above supports either, the gap is ~1 dB.

Not changed in this task: `bakeCoarseFirst`'s default (tools source is off limits here); the proposal is a
one-word change in `coarse-first.ts` plus its docs and `K4-5-coarse-first.md` once approved.
