# K4.16 / K4.18 handoff: coarse-first `.nvdb` delivery and ZIP writes

Implements option (a) of [docs/design/K4-5-coarse-first.md](../../dev/design/K4-5-coarse-first.md): a small preview grid
first in the same multi-grid `.nvdb`, then the full grid. Also K4.18: `writeNvdb` with NanoVDB's ZIP codec.

## API

`@pmndrs/vdb/tools`:

```ts
bakeCoarseFirst(source: Uint32Array | VdbGrid | VdbFile, {
  previewResolution?: number | number[];   // default 48; several = a chain, written coarsest first
  filter?: 'point' | 'box' | 'trilinear';  // default 'box'
  quantize?: 'fp8' | 'fpn' | 'none';       // previews, default 'fpn'
  tolerance?: number;
  fullQuantize?: 'fp8' | 'fpn' | 'none';   // default: as given for an image, `quantize` for a .vdb grid
  codec?: 'none' | 'zip';                  // default 'zip'
  zipLevel?: number;                       // default 9
  sourceGridName?: string;
}): Uint8Array                             // [<name>.lod48, <name>]

writeNvdb(images, { codec?: 'none' | 'zip', zipLevel?: 0..9 }): ArrayBuffer

new NvdbStreamReader({ maxGridBytes?: 1 GiB, maxNameBytes?: 64 KiB })
  .push(chunk): NvdbStreamGrid[]           // grids this chunk completed
  .end()                                   // throws NvdbFormatError if the stream stopped mid-segment
  .grids                                   // every FileMetaData seen so far (the full grid's size before the preview's data)
  .bytesReceived / .gridsEmitted / .atBoundary
NvdbStreamGrid = { index, metadata: GridMetadata, image: Uint32Array, bytesReceived, lod: number | null, baseName }
readNvdbStream(stream | asyncIterable, options): AsyncGenerator<NvdbStreamGrid>   // cancels the stream on break
nvdbLodName(name, res) / parseNvdbLodName(name)   // '<name>.lod<res>' <-> { baseName, lod }
NvdbFormatError extends VdbFormatError
```

`@pmndrs/vdb/three` (engine-free glue; here because `tools` may not import the core):

```ts
vdbStreamCoarseFirst(pool, source: Response | ReadableStream | AsyncIterable, {
  gridName?, label?, reader?, signal?,
  onGrid?: (e: { id, grid, final, action: 'add' | 'replace', bytesReceived, voxelRatio }) => void,
}): Promise<{ id, shown, firstBytes, fullBytes }>
```

It calls `pool.add(preview, { capacity: largest grid of the family })` when the first grid of the family
completes, then `pool.replace(id, finer)` for each finer grid, and resolves (cancelling the rest of the stream) when
the full grid is in. A segment lists every FileMetaData before any grid data, so the full size is known when the
preview is added and the swap is in place (no pool growth, no `version` bump; the e2e checks it). Callers
re-derive in `onGrid`: `densityScale × voxelRatio` (the material integrates per index voxel), the proxy geometry
from `pool.info(id)`, and a brick majorant if they use one (`replace` drops it).

## Format: what changed in the reader and writer

NanoVDB's `io::Segment` (IO.h at the pin) writes a FileHeader, then **every** grid's FileMetaData + name, then
every grid's data; a file is one or more segments (`writeGrids` writes one per handle). Our `writeNvdb` and
`NanoVDBFile` interleaved metadata and data per grid. That is the same bytes for one grid (every fixture and every
existing caller), but a multi-grid file of ours could not be read natively, and a native multi-grid file could
not be read by us. Both now follow `io::Segment`, and `NanoVDBFile` reads several segments (trailing bytes that
are not a segment throw). Single-grid output is byte-identical to before.

ZIP framing is `io::Internal::write`'s: a u64 LE compressed size, then a zlib (RFC 1950) stream, as zlib's
`compress()` writes it; `FileMetaData.fileSize` = 8 + compressed bytes; both codec fields are 1. We deflate with
fflate at level 9 (native: zlib level 6), so the framing is native and the compressed bytes differ (DIVERGES V28).
Our reader already decoded ZIP, with the bounded inflate from K4.1 (output allocated at gridSize + 1); the inflate
moved into `inflateZipGrid`, shared by both readers.

Previews are identified by name (`<name>.lod<resolution>`, DIVERGES V29). The full grid keeps the source name.

## Stream reader hardening

Every allocation is a declared size checked first: `gridSize` must be a safe integer, at least 672 bytes and at
most `maxGridBytes`; a name at most `maxNameBytes`; a ZIP payload at most zlib's `compressBound(gridSize)` + 64,
and it inflates into gridSize + 1 bytes at most. The FileHeader version and codec, a zero grid count, the grid
type (at its FileMetaData, before its data downloads) and the image's own `mGridSize` are checked. Malformed
data is `NvdbFormatError` (a `VdbFormatError`); BLOSC, raw `NanoVDB1` buffers and unsupported grid types are
`VdbUnsupportedError`. A failed reader rethrows on every later call. Memory: the current segment's metadata and
the grid being filled, never the whole file; each emitted image is its own 4-byte-aligned buffer.

## Measured (smoke.vdb, `[density.lod48, density]`, box, FpN)

`node scripts/bake-coarse-first.mjs` (Node, gzip level 9) and the e2e (headless Chromium, SwiftShader;
`CompressionStream('gzip')`, the browser's default level). Sizes are deterministic.

| | Node script | Browser e2e |
|---|---|---|
| Preview image / full image (decoded) | 320.7 KiB / 1,372.2 KiB | same |
| File, codec ZIP | 666.3 KiB | 666.3 KiB |
| File, codec NONE | 1,693.3 KiB | 1,693.3 KiB |
| File, codec NONE + gzip | 654.5 KiB (level 9) | 658.8 KiB |
| File, codec ZIP + gzip | 665.0 KiB | 665.0 KiB |
| **First paint, ZIP, no HTTP compression** | **12.3 KiB** (12,548 B, exact) | **13.0 KiB** at 1 KiB chunks (file offset 12,548 B) |
| First paint, NONE + gzip | 12.0 KiB (64-byte steps) | 12.3 KiB (256-byte chunks, upper bound) |
| First paint, ZIP + gzip | 11.6 KiB | 11.8 KiB |
| First paint, NONE, no compression | 321.0 KiB | — |

Gate: his `smoke.wvdb` needs 14.8 KiB (15,155 B) before LOD0 draws. All three compressed paths pass in the
browser. The e2e counts are transferred bytes when `pool.add` ran, in whole chunks, so they overstate the exact
offset by up to a chunk (plus up to a couple of 256-byte chunks buffered in the `DecompressionStream` pipe).

The design's 11.9 KiB (gzip, NONE) assumed the interleaved layout; the native layout puts the full grid's
FileMetaData (184 B) before the preview's data, hence 12.0 KiB. The ZIP file is 11.8 KiB larger than NONE +
Node gzip 9 (fflate's deflate vs zlib's).

Gates: `pnpm typecheck`, `pnpm build`, `pnpm test` (56 files, 1,103 passed, 10 skipped), the new e2e, and the

## Native compatibility (owner check, K4.17)

Not verified on native tools. What should hold, from IO.h at the pin:

- The file is one `io::Segment` with two grids: `nanovdb_print`/`readGridMetaData` should list both; `readGrid(is,
  "density")` compares names (our `nameKey` is 0, which it accepts) and returns the full grid; `readGrid(file)`
  with no name or index (and any "grid 0" consumer) gets the **preview**.
- Codec ZIP needs native tools built with zlib (`NANOVDB_USE_ZIP`); otherwise they throw "ZIP compression codec
  was disabled during build". `bakeCoarseFirst({ codec: 'none' })` writes a file every build reads, and first
  paint then needs HTTP compression.
- Our grid images keep `mGridIndex` 0 / `mGridCount` 1 each; native `readGrid` calls `updateGridCount` on load,
  so this should not matter.
- EmberGen and other `.nvdb` consumers: unknown; record which grid they show.

Suggested test (K4.17): `node scripts/bake-coarse-first.mjs --out smoke.coarse.nvdb` (ZIP) and `--codec none`,
then in the parity Docker image `nanovdb_print` both, `nanovdb_convert` both back to `.vdb`, and the 10-line
`io::readGrid(file, "density")` check against the single-grid file. Fallback if a grid-0 reader matters: option
(b), a separate preview file (same bake: `writeNvdb([preview])`).
