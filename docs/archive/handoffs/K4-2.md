# Handoff: K4.2 — vector and point grids in the `.vdb` parser (plus K4.7)

The pure-TS `.vdb` parser in `@pmndrs/vdb/tools` now reads:

- vector grids (`vec3s`, `vec3d`, `vec3i`), which build NanoVDB `Vec3f` grids;
- point data grids (`ptdataidx32`), which decode to a point list;
- OpenVDB 12.1 half-float grids that omit empty value arrays (K4.7).

Every sample in `fixtures/vdb-samples` now parses, all grids included.

Format authority: OpenVDB and NanoVDB at the repo pin `a532de55`. Headers used: `io/Compression.h`,
`tree/{Root,Internal,Leaf}Node.h`, `Grid.h`, `points/{PointDataGrid.h, AttributeArray.h, AttributeSet.cc,
StreamCompression.cc}`, `math/QuantizedUnitVec.*` and `nanovdb/tools/GridStats.h`. They were fetched read-only to
the scratchpad; the sparse checkout only has NanoVDB.

## What changed

All changes are in `packages/vdb/src/tools/**` and `packages/vdb/test/tools/**`.

### Parser

**Value formats** (`vdb/compression.ts`). A `ValueFormat` has `components` (1 or 3) and a component kind (`f32`,
`f64`, `i32` or `u32`).

- `readCompressedValues` reads `numValues * components` scalars. That covers raw, zip and Blosc storage, half or
  full width, and active-mask expansion with the inactive fill values (which are written full width even in
  half-float grids).
- `readFullValue` reads the root background and root tile values, which are always full width.
- Half storage is honoured only for real types, following `RealToHalf<T>::isReal`. An integer grid saved "as
  half" stays full width.
- Values are decoded into a `Float32Array`. That is exact for f32, and for i32/u32 below 2^24. f64 is narrowed.

**K4.7: the rule from the source.** `io::HalfWriter<true, T>::write` and `HalfReader<true, T>::read` both
`return` when `count < 1`, so an empty half-float array has no payload at all: no Blosc or zip i64 either.

- Full-width and integer arrays go through `readData`. With Blosc or zip, that still writes the size field for
  count 0. bunny_cloud stores a 16-byte empty Blosc frame there.
- So the parser reads nothing when `half && activeCount < 1`. It does not use a retry or a writer-version guess.

The K4.1 handoff guessed that "older writers write the i64 for zero counts". That was wrong:

- The v222 half-float samples (sphere, cube, teapot, smoke) are not zip-compressed (compression = active mask
  only), so count 0 reads nothing under either convention.
- I checked this by dumping the bytes at every empty node.

**Grid API** (`vdb/types.ts`, `vdb/grid.ts`). This is a breaking type change: `VdbGrid` is now a discriminated
union on `valueType`.

| Type | `valueType` | `components` | `background` | `readValue().value` | Extra fields |
|---|---|---|---|---|---|
| `VdbFloatGrid` | `float` | 1 | `number` | `number` | — |
| `VdbVec3Grid` | `vec3s`, `vec3d`, `vec3i` | 3 | `[x, y, z]` | `[x, y, z]` | — |
| `VdbPointDataGrid` | `ptdataidx32` | 1 | `number` | the voxel's end offset | `pointCount`, `attributes`, `groupNames`, `points()` |

- Vector leaves hold 1536 interleaved values. Vector tiles are `[x, y, z]`.
- New exported types: `VdbFloatGrid`, `VdbVec3Grid`, `VdbPointDataGrid`, `VdbPointList`,
  `VdbPointAttributeInfo`, `VdbPointAttributeArray`, `VdbValueType`, `Vec3Tuple`.

**Point data grids** (`vdb/points.ts`, new). This follows OpenVDB's multi-pass I/O (`Grid::readBuffers`): a
`u16` pass count, then the tree walked once per pass.

- Per leaf, the passes read:
  - the voxel-buffer size;
  - the descriptor (shared via header bit 1) and the array metadata;
  - page headers per attribute;
  - the voxel buffer (raw 0xFFFF or Blosc);
  - the page bodies, or non-paged buffers.
- Paged streams follow `PagedInputStream` exactly: a page header is read when an array starts a new page.
  - Blosc pages padded to 48 bytes are accepted, per the rule in `bloscDecompress`.
  - Page bytes stay views into the file until `points()` runs.
- `points()` returns:
  - world `positions`: index-to-world of (voxel ijk + P);
  - every other decodable attribute;
  - group membership by name (`Descriptor::groupIndex`: sorted `uint8`/`grp` arrays, bit = offset % 8);
  - `skipped`: attributes whose type and codec it cannot decode.
- Codecs:
  - `null`, including all OpenVDB scalar, vec, quat and mat type names;
  - `trnc` (half, int16);
  - `fxpt8/16` and `ufxpt8/16`, with OpenVDB's f32 arithmetic;
  - `uvec`: `QuantizedUnitVec::unpack`. The 8192-entry weight table is generated, not copied, and equals
    OpenVDB's table bit for bit (scratch check against `QuantizedUnitVec.cc`);
  - `str`, as raw u32 indices.
- Uniform and constant-stride arrays are handled. Variable-stride arrays are skipped.
- Validation: end offsets must be monotonic, and every array's size must equal the leaf's point count.

**Bug fix, pre-v222 leaves.** `LeafNode::readBuffers` reads the value mask *before* the origin and buffer count.
Our reader had them the other way round, and the synthetic writer mirrored that. No corpus file is pre-222.

### NanoVDB

- **Vec3f build** (`nanovdb/{bytes,leaf-codec,tree,stats,serialize,build-from-vdb}.ts`). It has:
  - `VEC3F_LAYOUT` (GridType 6);
  - root 96 bytes, root tile 32 (value at 20), table stride 16, upper 532,544, lower 66,624, leaf 6,272 (table at
    128);
  - all checked against the vendored stride tables.
- **`VEC3F_LEAF_CODEC`**. `buildFromLeavesDetailed` and `buildTreeFromLeaves` take a `components` setting. Tile
  and background values are `number | [x, y, z]` (`TileValue`).
- **Stats follow `GridStats.h` `Stats<Vec3f, 1>`** (rank 1):
  - `min`/`max` are the *vectors* with the least and greatest f32 `lengthSqr()`, first one wins on ties;
  - `ave`/`std` are the mean and population std of `lengthSqr()`, not of the components. They are f32
    (`FloatTraits<Vec3f>` is float);
  - tiles are weighted by the child slot count, as before;
  - the class is `Vec3StatsAccumulator`.
- **`buildFromVdb`** dispatches on the value type:

  | Source grid | NanoVDB result |
  |---|---|
  | float | FLOAT |
  | vec3s, vec3d, vec3i | Vec3f |
  | point data | `VdbUnsupportedError` |

  The grid class maps `staggered` to `Staggered` (3).
- **CPU oracle.** New `readValueVec3(image, ijk)` and `sampleTrilinearVec3(image, xyz, { outside })`. The second
  is componentwise, with the same taps and lerp order as `sampleTrilinear`. `readValue` on a VEC3F image throws
  and points to `readValueVec3`.
- **Other tools.**
  - `inspect` reports Vec3f with correct section sizes.
  - `writeNvdb` already carried any grid type.
  - `NanoVDBFile` still rejects Vec3f, which is in scope for later (GPU and pool are out of scope).
- **`.wvdb`.** `wvdbSourceFromVdbGrid` throws for non-float grids. `vdbToWvdb` bakes float grids only and skips
  vector and point grids (his CLI bakes them; not ported).

## Open issues

1. **No native Vec3f parity.** Our Vec3f image was not compared with `nanovdb_convert` output (no Docker or
   native tools here). The stats semantics come from reading `GridStats.h`. The f32 `lengthSqr` might differ
   from native by an FMA contraction in rare ties.
2. **`points.ts` is not hardened against hostile input** the way K4.1 hardened Blosc.
   - What is in place: decompression is capped by the page header and array sizes, and counts are checked.
   - What is missing: a page header can still claim up to 2 GiB of output, and a uniform array's `size` is
     unbounded by bytes.
3. **Asset-gated tests that fail only with `MJURCZYK_OPENVDB_DIR` set.** In K4.3's `wvdb-read.test.ts`, 3 such
   tests fail. Nothing here touches that code. The causes:
   - our symlinked `fixtures/vdb-samples` now holds `sphere_points.vdb` and `bunny_cloud.vdb`, and `vdbSample()`
     prefers ours over his;
   - ours are different files from the ones his `.wvdb` headers hash, so the source SHA check fails;
   - a level-set test takes ~7 s against the 5 s default timeout.
4. **Inactive values in compressed arrays are still 0** (K4.8, unchanged), now also for vectors.

## Review + hardening

Branch `k42-hardening` on aef306d. Format authority: OpenVDB at the pin a532de55 (`io/Compression.h`,
`tree/LeafNode.h`, `points/{PointDataGrid.h, AttributeArray.h, AttributeSet.cc, StreamCompression.cc}`,
`math/QuantizedUnitVec.{h,cc}`, `version.h.in`, fetched read-only to the scratchpad) and NanoVDB `tools/GridStats.h`
from the sparse checkout.

### Review: what checks out

- **K4.7 half-float rule.** `HalfReader<true, T>::read` and `HalfWriter<true, T>::write`/`writeSize` all `return`
  when `count < 1`, so an empty half array has no payload, not even the Blosc/zip i64. `HalfReader<false, T>` is plain
  `readData`, which reads the i64 for count 0 (`bloscFromStream`, `unzipFromStream`). `count` is `tempCount`: the
  active count when mask compression applies and metadata is not `NO_MASK_AND_ALL_VALS`, else the node size. That is
  exactly our `half && onDiskCount < 1`. "Half" is `RealToHalf<T>::isReal`: float, double, Vec2s/d, Vec3s/d. Vec3i
  and PointDataIndex32 stay full width, as we do. The early return is in OpenVDB v2.0.0 and v3.0.0 too (checked by
  tag on GitHub), so it holds for every writer that could produce these files, not only 12.x.
- **Codecs.** `FixedPointCodec`: `float(s) / float(max)`, then `PositionRange` subtracts 0.5 (`fxpt`) or `UnitRange`
  leaves it (`ufxpt`), in f32. `TruncateCodec`: half to float, short to int. `UnitVecCodec`: `QuantizedUnitVec::unpack`.
  The generated weight table equals OpenVDB's literal table bit for bit (all 8192 entries, scratch check). There is
  now also a test that compares 11 entries against literals copied from `QuantizedUnitVec.cc`. `StringCodec` arrays
  are raw u32 indices. Group arrays are `uint8`/`grp`, `groupBits` is 8, and the arrays are sorted by attribute index.
- **Positions.** `P` is a voxel-space offset from the voxel centre in [-0.5, 0.5] (the `PositionRange` comment).
  World = `indexToWorld(ijk + P)`, in double, then stored as f32. That matches.
- **Strides.** `WRITESTRIDED` is set when `stride() != 1`. `stride()` is 0 for variable-stride arrays, whose
  `strideOrTotal` is the total size. `dataSize` is `size * stride` or the total. A uniform array stores one
  `StorageType` whatever its stride (`arrayMemUsage`). Transient arrays are dropped from both the descriptor and the
  metadata (`writeDescriptor` uses `duplicateDrop`), so the counts stay consistent.
- **Passes, descriptors and pages.** These match `PointDataLeafNode::readBuffers`:
  - the shared-descriptor state is cleared in pass 0;
  - the voxel-buffer specialization reads a u16 size, 0xFFFF for raw, Blosc otherwise, and ignores the grid's
    compression and half flags;
  - `PagedInputStream::createHandle`/`read` behave as ours do;
  - `PageSize` is 1 MiB, and an array larger than that gets its own page.
- **Pre-222 leaves.** `LeafNode::readBuffers` loads the value mask, then (version < 222) the origin and `numBuffers`.
  The fix is right.
- **Vec3f NanoVDB.** The layout offsets re-derive by hand (leaf: header 80, min 80, max 92, ave 104, std 108, table
  at 128, 6,272 bytes; lower and upper table stride 16; root tile value at 20). `Stats<Vec3f, 1>`:
  - `Pair::scalar = v.lengthSqr()` in float;
  - min and max are the vectors, compared strictly, so the first one wins;
  - `mAvg`/`mAux` run a double Welford over `lengthSqr` (squared lengths, not lengths) and are stored as f32;
  - internal nodes add active tiles (slot order) before children, as `tree.ts` does.

### Review: findings, ranked

| # | Severity | Finding | Fix |
|---|---|---|---|
| 1 | high | Every pass visited every leaf, so `numPasses` (u16, up to 65535) times the leaf count was looped with no bytes behind it. A leaf with more attributes than `(numPasses - 4) / 2` had arrays that were silently never read. | Each pass now visits only the leaves that own the array. A leaf whose attributes exceed the passes is a `VdbFormatError`. Old code: 762 ms on 4096 leaves; now 69 ms (test time including the write). |
| 2 | high | Uniform arrays store one value for any point count, and strides are u32. A tiny file could claim 4 billion points, or a stride of 2^32 − 1, and `points()` would call `new Float32Array(count * 3)` or `new T(count * stride * components)`. The result was a RangeError or a multi-GB allocation. Old code: the stride case allocated about 11 GB of RSS and was still running after 6 minutes. | Parse: total points × 12 must be ≤ `MAX_POINT_EXPANSION` (256) × file bytes. Decode: a `DecodeBudget` of 256 × file bytes is charged before every output array and every decoded page, and short-lived buffers are checked against it. The real samples need under 3×. |
| 3 | high | Page headers were unbounded: a Blosc page could claim up to 2 GiB, which became `decompressBlosc`'s `maxBytes`. | 5 | medium (memory) | Decoded Blosc pages were cached on the `PointPage` objects, which the grid keeps. After `points()`, every decompressed page stayed alive next to the output (waterfall: up to about 180 MB). | The page cache is now local to one `decodePoints` call. | 6 | low | u64 fields were narrowed with `Number()` before their checks (array byte count, descriptor skip, attribute index). A constant stride of 0 was accepted. | Compared as bigint, with clean errors. Stride 0 is rejected. |
| 7 | low | A repeated attribute name gave two attributes with the same name. OpenVDB's `std::map` keeps the first and leaves the other unnamed. | 8 | low | `ByteReader.string()` built strings with a per-byte `+=`. | Chunked `fromCharCode`: 64 MiB takes 0.28 s instead of 3.3 s. |

**Not fixed** (noted for later):

- **a.** `parse.ts` accepts any file version ≥ 213. OpenVDB rejects versions above `OPENVDB_FILE_VERSION` (225 at the
  pin). The pinned headers have no code paths for 224 or 225.
- **b.** `readMetadataMap` writes into a plain object, so a metadata name `__proto__` sets its prototype. This dates
  from K4.1. Suggestion: `Object.create(null)` or a `Map`.
- **c.** Point-grid `readValue` returns end offsets through `Float32Array.from(offsets)`, which is not exact above
  2^24 points in one leaf.
- **d.** The Vec3f stats edge cases:
  - if every `lengthSqr` overflows to +Inf, native min stays `(FLT_MAX, FLT_MAX, FLT_MAX)`; ours stays `[0, 0, 0]`;
  - ave/std use sum and sum of squares, where native uses Welford (a double-rounding difference, as on the scalar
    path).
- **e.** A leaf with `numBuffers != 1` (before v222) is rejected. OpenVDB reads and discards the extra buffers.

### No independent oracle (compared only against our own synthetic writer)

These are checked only against `synthetic-points.ts`, which the same agent wrote from the same reading:

- `uvec` decode on real data;
- `trnc` on scalar float, `fxpt8`, `ufxpt16` and `str`;
- groups, strided arrays, unshared descriptors;
- non-paged Blosc arrays, raw non-paged arrays.

The samples cover only P as `fxpt16` (oracle: his `sphere_points.wvdb`, bit-exact bbox) plus waterfall's Cd
(`ufxpt8`), id (`int32`) and v (`trnc` vec3s). For those three the checks are self-consistency only:

- Cd values are exact 8-bit codes;
- ids are unique;
- v has no check.

The Vec3f image has no native `nanovdb_convert` parity. Its stats test is a brute force written from the same reading
of `GridStats.h`; I re-read the header for this review and it agrees. The K4.7 rule does have an independent oracle:
OpenVDB's own `file_voxel_count` and `file_bbox` for bunny, icosahedron and fire.

Suggested oracle: dump waterfall's Cd, v and id with OpenVDB's Python bindings (or `vdb_print` plus a small C++
dumper) and compare them per point.

### Hostile tests

`test/tools/points-hostile.test.ts` has 38 tests. Each hostile case asserts:

- the error class and its message;
- under 200 ms;
- no `Uint8Array` or `Float32Array` longer than 1 Mi elements built during the call.

Files are made by `synthetic-points.ts`, which gained `tamper` hooks: `numPasses`, `arrayMeta`, `pageHeaders`,
`descriptor`, `storedOffsets`. Every case runs in 0 to 3 ms, except:

- numPasses 65535 × 4096 leaves: 69 ms (write included);
- a 4 MiB metadata string: 43 ms;
- the at-the-bound decode: 30 ms.

Run against the pre-hardening `points.ts`:

- 16 cases fail or hang (5 of them only on the message wording, for example a rounded `Number(u64)` in the text);
- the 65535 × 4096 case takes 762 ms;
- the uniform stride of 2^32 − 1 hangs, with 11 GB RSS;
- the page-header, 4-billion-point and group-offset cases were accepted at parse.

The vector cases and the weight-literal test passed before too: they lock existing behaviour.
