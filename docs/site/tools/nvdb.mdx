`.nvdb` is NanoVDB's file format: a header, then each grid's metadata and image. It is the exact format here
(D14): sparse, full resolution, read and written byte for byte.

## Read

`NvdbFile` parses a file with any of NanoVDB's codecs: NONE, ZIP and BLOSC. BLOSC covers what NanoVDB writes
(`nanovdb_convert -b/--blosc`: LZ4 frames, split at 1 GiB) and what NVIDIA Warp writes (`Volume.save_to_nvdb(codec="blosc")`:
BloscLZ), as NanoVDB 14 reads both. A grid image decompressed from a ZIP or BLOSC file is a copy; from an uncompressed
one it may be a view of the source buffer (`isGridImageZeroCopy(i)`). Files from NanoVDB 32.x (OpenVDB 10 to 14) load;
another major version throws `VDBUnsupportedError`.

{/* snippet: nvdb-read */}
```ts
import { NvdbFile } from '@pmndrs/vdb/tools';

const file = await NvdbFile.fromURL(url); // or NvdbFile.fromArrayBuffer(bytes)
for (const meta of file.grids) console.log(meta.name, meta.gridType, meta.gridClass, meta.voxelSize);

// The grid image is what VDBGridPool.add() takes, byte for byte. Float, Fp4, Fp8, Fp16, FpN and Half grids load.
const image = file.gridImage(0); // decompressed when the file is zipped
```

`NvdbFile` loads Float, Fp4, Fp8, Fp16, FpN and Half grids. It is the one reader: there is no separate `readNvdb`, so use
`NvdbFile` for bytes you already hold (`fromArrayBuffer`, or `fromURL` for a fetch) and `readNvdbStream` for a stream.
Native `nanovdb_convert` writes Float, Fp8 and FpN; `vdbQuantize(image, 'fp4' | 'fp16' | 'half')` makes the others (native
NanoVDB 13.2+ writes Half grids only from C++, `createNanoGrid<…, nanovdb::Half>`).

## Write

`writeNvdb(images, { codec, zipLevel })` writes any number of grid images to one file. `codec` is `'none'` or `'zip'`
(BLOSC is read, not written).
`build-dense` on [building grids](/tools/build-and-quantize) shows it in use.

## Stream

`readNvdbStream(source)` takes a `Response`, a `ReadableStream` or any async iterable of byte chunks, and yields each
grid as soon as its bytes are complete, whatever the codec (a BLOSC grid decodes chunk by chunk into its own buffer).

{/* snippet: nvdb-stream */}
```ts
import { readNvdbStream } from '@pmndrs/vdb/tools';

const response = await fetch(url);
// Each grid is emitted as soon as its bytes (raw or zipped) are complete, so the first grid can be
// on screen while the rest downloads.
for await (const grid of readNvdbStream(response, { onProgress: (p) => console.log(p.bytesReceived, p.bytesTotal) })) {
    console.log(grid.index, grid.baseName, grid.lod, grid.image.byteLength);
}
```

Under it, `NvdbStreamReader` is the push parser (`push(chunk)` returns the grids a chunk completed). Hostile input is
bounded: `maxGridBytes` and `maxNameBytes` cap what a header may claim.

## Coarse-first

`vdbBakeCoarseFirst(source, options)` writes one `.nvdb` holding `[<name>.lod48, <name>]`: a coarse preview first, the
full grid after it. A reader that streams (`readNvdbStream`, or `vdbStreamCoarseFirst` in [three.js](/three/compute-and-streaming))
shows the preview as soon as its bytes arrive, then swaps in the full grid. The preview filter defaults to
`'trilinear'` (D26); keep `'box'` for thin or high-frequency data.

{/* snippet: coarse-first-bake */}
```ts
import { vdbBakeCoarseFirst, nvdbLodName, parseNvdbLodName } from '@pmndrs/vdb/tools';

// One .nvdb holding [<name>.lod48, <name>]: a coarse preview first, the full grid after it.
const file = vdbBakeCoarseFirst(image, { previewResolution: 48, quantize: 'fp8', fullQuantize: 'fpn', codec: 'zip' });

console.log(nvdbLodName('cloud', 48)); // the name of the preview grid
console.log(parseNvdbLodName(nvdbLodName('cloud', 48))); // { baseName: 'cloud', lod: 48 }
```

## CPU reads

`vdbReadValueCpu` and the sampling functions are the WGSL module's tree descent in TypeScript, so you can check GPU results
or read voxels with no GPU. They take a grid image and **index-space** coordinates. `vdbReadValueCpu` is the exact f64 decode;
`vdbReadValueF32` matches the shader's f32 arithmetic and is the oracle for GPU parity. They read Float, Fp4, Fp8, Fp16, FpN and Half
grids (and `vdbReadValueVec3` / `vdbSampleTrilinearVec3` read Vec3f).

{/* snippet: cpu-reads */}
```ts
import { vdbReadValueCpu, vdbSampleTrilinear } from '@pmndrs/vdb/tools';

// The same tree descent as the WGSL module, in TypeScript: an oracle for GPU results, no GPU needed.
// Index space: the integer coordinates are voxels. (Float, Fp4, Fp8, Fp16, FpN and Half grids.)
console.log(vdbReadValueCpu(image, [10, 20, 30])); // { value, active }
console.log(vdbSampleTrilinear(image, [10.5, 20.25, 30])); // continuous index-space sample
```

`vdbGridStatsCpu` and `vdbDecodeToAtlasCpu` are the CPU versions of the core's compute tools. Every WGSL entry point
also has a CPU twin used as its test oracle (`hddaWalk`, `rayClip`, `nodeMax`, the frame renderer's passes); those live
in the repository's tools internals (`src/tools/internal.ts`), not in the published API (D32).

## Errors

Every error `@pmndrs/vdb/tools` throws on bad input is a `VDBToolsError`, so one `instanceof` covers every format.
Its `code` says what went wrong:

| Class | `code` | When |
| --- | --- | --- |
| `VdbFormatError` | `VDB_BAD_VDB` | The bytes are not a valid `.vdb` (bad magic, truncated, corrupt). |
| `NvdbFormatError` | `VDB_BAD_NVDB` | The bytes are not a valid `.nvdb` (from `NvdbFile` and the stream reader alike). |
| `WvdbFormatError` | `VDB_BAD_WVDB` | The bytes break the `.wvdb` spec. |
| `VDBUnsupportedError` | `VDB_UNSUPPORTED` | Valid data these tools don't handle (another NanoVDB major version, a Zstd Blosc frame, a rotated map, ...). |
| `VDBToolsError` | `VDB_BAD_OPTION` | An argument or option is out of range or inconsistent. |
| `VDBToolsError` | `VDB_BAD_IMAGE` | A `Uint32Array` argument is not a NanoVDB grid image. |
| `VDBToolsError` | `VDB_UNSUPPORTED_GRID_TYPE` | The operation doesn't take the grid's type (e.g. quantizing a Vec3f grid). |

A failed `NvdbFile.fromURL` fetch is a plain `Error`: it is the network, not the input.
