Both are supported by `@pmndrs/vdb/tools`, for different jobs (D14).

| | `.nvdb` | `.wvdb` |
| --- | --- | --- |
| What | NanoVDB's file format: grid images in a small container | mjurczyk's WebVDB delivery format (spec v0.5) |
| Data | Sparse tree at full resolution; Float, Fp4, Fp8, Fp16, FpN | Dense bricks at several LODs, resampled to a target resolution (8-bit texels in the dense renderer source) |
| Read on the GPU | Directly: the file's grid image is what the pool holds, byte for byte | After a conversion to 3D textures (dense source) or to a NanoVDB grid (sparse source) |
| Read | `NvdbFile`, `readNvdbStream` | `readWvdb`, `WvdbStreamReader` |
| Write | `writeNvdb` | `writeWvdb`, `vdbToWvdb`, `nvdbToWvdb`, `bakeWvdb` |
| Progressive loading | `vdbBakeCoarseFirst`: one file, `[<name>.lod48, <name>]` | Native: LODs are stored coarsest first, and byte ranges per LOD |
| Size | Measured: at equal resolution, FpN is 474 KiB on the smoke sample | 790 KiB on the same sample |

## Which to use

- **Use `.nvdb` for the data you render.** It is the exact format: nothing is resampled, and the GPU reads the bytes
  you wrote. It is the format of `VDBGridPool`, `VDBVolumeMaterial` and the sparse source.
- **Use `.wvdb` when you already have it**, or when you want his delivery path: it has coarse-first streaming and an
  existing user base. The dense frame-renderer source reads it.
- **From a `.vdb`**, go to `.nvdb` with `buildFromVdb` (then `quantize` to shrink it), or to `.wvdb` with `vdbToWvdb`.

## Between them

- `.wvdb` to `.nvdb`: `wvdbDenseToNvdb(wvdbDenseVolume(file))` converts a LOD voxel for voxel into a Float grid
  (texel `k` becomes `k / 255`, zero texels inactive). It also returns `textureIndexBox`, to pass as `indexBox` to
  `vdbSparseSource`.
- `.nvdb` to `.wvdb`: `nvdbToWvdb(image, options)`. It samples over the bbox, point-sampled by default like his CLI
  (D27); pass `sampling: 'box'` for sources much finer than the texel grid.

## Provenance

`.wvdb` reading, writing and baking are ported from [mjurczyk/openvdb](https://github.com/mjurczyk/openvdb) (MIT),
pinned at `75e7345` (v0.26.0). Where the code departs from his, the divergence is recorded in
[DIVERGES.md](https://github.com/pmndrs/vdb/blob/main/DIVERGES.md).
