# K3.2d / K3.2e handoff: fast sparse sampling, HDDA re-measured, stats follow `pool.replace`

On the worktree branch from `v2` (9c14cfa). Status: K3.2d ✅, K3.2e ✅. Every timing below is **provisional** (D25):
Apple M5 Pro (`apple metal-3`), installed Chrome 157.0.8103.80 with `timestamp-query`, but the machine was shared
(load average 4.4–6 during the final runs, up to ~20 earlier while other agents ran SwiftShader suites). Ratios are
paired runs minutes apart in one script; single figures are ±15%. Images are unchanged: the new sampler is
bit-identical to the old one.

## Where the cost was (step 1)

'frame' density pass, sparse `'coarse-pyramid'`, 1080p, froxels 512x512x24, 32 sub-steps, with level 0 replaced
by cheaper stand-ins (a temporary switch, removed; indicative: another timing run shared the GPU):

| level 0 | cloud04 | WDAS quarter (Fp8) |
|---|---:|---:|
| `vdbSample` (K3.2) | 5.31 ms | 12.80 ms |
| one `vdbReadValue` (nearest, one descent) | 1.80 | 3.97 |
| a constant | 0.90 | 1.34 |
| dense source (for scale) | 0.92 | 0.99 (128³ bake) |

So the whole sparse/dense gap is level-0 sampling, and most of it is the 7 extra taps, not the descent: with the
accessor's one-leaf cache, a cell that straddles leaves alternates leaves in the x-fastest tap order and re-walks
from the lower node; in a SIMD group some lane almost always does, so every lane pays it.

Candidate (a) as specified, the **same-leaf fast path** (one descent, 8 taps decoded from the leaf when all share
it, else `vdbSample`), was built first and lost: in the microbenchmark `fast-init` was 15–20% slower than `init` on
every asset and stride; in the real pass it was 10–30% slower on bunny, smoke and WDAS (WDAS density 16.0 vs
12.8 ms) and ~10% faster on cloud04. The 1/3 of lanes that fall back make most SIMD groups run both paths. The
shipped `vdbSampleFast` instead gives every lane the same work (8 lower-node lookups) and falls back only on
lower-node faces (1/128 per axis, spatially coherent). (c) **accessor caching**: the vendored accessor caches
leaf/lower/upper, but the sparse source called `vdbAccessorInit` per sample; alone, reusing it changes nothing
(the per-tap divergence dominates), with `vdbSampleFast` (which starts from the cached lower node) it is worth
another 10–25%.

**Recommendation: keep `hdda` off (D30 stands).** It is never a gain in 12 paired runs, and the default
`'coarse-pyramid'` pays 3.0–3.4× on the clouds (K3.2c: 2.1–3.3×): faster samples make skipping them worth even less,
while the walk (8 `vdbNodeMax` per 8³ cell, its own fresh accessor) did not get faster. WDAS with the pyramid stays
the only near-tie. Recorded as D31. A cheaper bound (a per-froxel early-out on the pyramid's coarse level, or the
walk on the cached accessor) would be a new A/B, not this default.

## Design note: a brick cache (K3.2f, not built)

What remains after K3.2d is per-tap work: a level-0 sample is still 8 child-mask → child → value load chains plus
the Fp decode, against one filtered fetch on the dense source. Only a brick layout removes that.

- **Layout.** A page table (one entry per 8³ block of the density index box: brick index + 1, or 0 for a
  tile/background block with its value in a side table) and an atlas of 9³-voxel bricks (the leaf plus a +x/+y/+z
  apron), so the 8 taps of any base voxel in a block sit in one brick.
- **Two formats.** (1) f32 atlas, 8 `textureLoad`s and the vendored `mix` structure: bit-identical to `vdbSample`,
  one dependent page load then 8 independent texel loads. (2) r16f atlas with one hardware-filtered fetch:
  dense-source speed, not identical (f16 values; 8-bit filter weights on Apple), so a parity bar like the dense
  source's identical-voxel A/B (≥ 38 dB).
- **Filling.** A core compute pass over the grid's leaves (a workgroup per leaf decodes 512 values plus the apron
  through the accessor), rebuilt on the grid's `imageRevision` like the pyramid. Either all leaves (simple; f32
  memory = leaves × 9³ × 4 B: ~1.5 MB for cloud04, tens of MB for WDAS quarter, so r16f or residency there) or only
  the leaves a frame touches (a feedback pass marks pages, a compaction allocates bricks, the next frame samples
  them: one frame of latency, misses fall back to the tree).
- **Work.** `createBrickAtlas(device, pool, id, { format })` next to `createBoxPyramid`, its CPU twin in `tools`, an
  atlas-vs-`readValue` parity spec, a source option (`level0: 'tree' | 'brick-f32' | 'brick-f16'`) and the A/B: two
  to three days with residency.
- **Expected.** Between the single-descent read (cloud04 density 1.8 ms) and the constant (0.9 ms) for f32; close to
  dense for r16f.

## Open

- K3.2f: the brick cache (above), the next order-of-magnitude step.
- K3.2g: rerun `--only=sampling`, `--only=hdda`, `--only=bench` with `--quiet` on a quiet machine (D25).
- HDDA stays off; a cheaper walk is its own A/B.
- `refreshStats` maps the whole image (WDAS quarter: 29 MB) and walks it on the CPU per changed frame; a sequence of
  large frames would want a GPU reduction (a non-zero sum/count kernel next to the pyramid's base pass).
- Mask/albedo/emission samples share the one cached accessor with the density (re-initialised when the grid id
  changes): fine for one channel, wasteful for masks; per-channel accessors if masked scenes matter.
