# K4.11 handoff: FpN size vs native

Question: our `quantize(float, 'fpn')` images are ~1.85× smaller than native `nanovdb_convert` FpN on the fog
primitives (sphere 2,879,072 vs 5,314,176 bytes). Different tolerance?

**Answer: no. Same tolerance, same oracle, same per-leaf bit widths, same leaf bytes. The native FpN image is
bigger because the pinned NanoVDB over-allocates it by exactly the size of its non-leaf sections (2,435,104
bytes on all three primitives).** Nothing to match; keep ours.

## Where the native bytes go

`inspect()` (memory breakdown; the leaf block is "whatever remains up to `mGridSize`"):

| sphere | native FpN | ours FpN |
|---|---|---|
| grid data + tree + root | 1,056 | 1,056 |
| upper (8 nodes) | 2,163,200 | 2,163,200 |
| lower (8 nodes) | 270,848 | 270,848 |
| leaf block | **2,879,072** | 443,968 |
| total | 5,314,176 | 2,879,072 |

The native "leaf block" (2,879,072) is the size of our whole image. Walking the native leaves (96 B header +
bits × 64 B each) ends at the same offset as ours. The surplus after the last leaf is 2,435,104 B =
672 + 64 + 320 + 2,163,200 + 270,848, the grid, tree, root, upper and lower sections, on sphere, torus and box.

Cause, in `nanovdb/tools/CreateNanoGrid.h` at the pin (`fixtures/downloads/openvdb-sparse`):

- `preProcess<FpN>` (L1061-1067) sets `mCodec[0].offset = NanoGrid::memUsage() + NanoTree::memUsage() +
  NanoRoot::memUsage(..) + NanoUpper::memUsage()*n2 + NanoLower::memUsage()*n1`, an **absolute** offset from the
  grid start (`dstNode<FpN,0>` is `PtrAdd(mBufferPtr, mCodec[i].offset)`, L650), then
  `mLeafNodeSize = getOffset(leafCount)`, the **absolute end** of the last leaf.
- The layout code (L940-942) treats `mLeafNodeSize` as a size: `mOffset.meta = mOffset.leaf + mLeafNodeSize`, and
  `mOffset.size` follows. The non-leaf prefix is counted twice. (The fixed-size path, L1004/L1162, sets
  `mLeafNodeSize = leafCount * leafSize`, a size, so Float/Fp4/Fp8/Fp16 are not affected: native Fp8 == ours byte
  for byte in size, 2,914,208 on the sphere.)
- The extra tail is never written. It is uninitialised heap: all zero in the sphere and torus files, 318,228
  nonzero bytes of garbage in the box file. The grid is valid and every reader works (ours and PNanoVDB follow the
  node offsets, not `mGridSize`), it is just 2.4 MB larger on disk and in a GPU buffer, and not deterministic.

Byte comparison of the first `ours.byteLength` bytes of each native FpN image against ours: 199 / 236 / 224
bytes differ (sphere / torus / box), all in the first ~800 bytes (GridData size and checksum fields, tree
offsets), none in the node tables or leaf data.

## Tolerance and oracle: identical

- Native `nanovdb_convert --fpn` / `createNanoGrid<FpN>` with no tolerance: `AbsDiff()` is `-1`, so
  `init(gridClass, background)` runs (`AbsDiff::init`, L258): FogVolume → `0.01`; LevelSet →
  `0.1 * background / 3`; anything else → `0.0`. Dithering off by default.
- Ours (`leaf-codec.ts` `makeFpNLeafCodec`): `FPN_DEFAULT_TOLERANCE = 0.01`, the same AbsDiff loop (1/2/4/8/16
  bits, float32 encode/decode, round-to-nearest = native's dither-off LUT), over all 512 values of the leaf.
  Per-leaf bit histograms match native exactly (below).
- The only behavioural difference: the default is fixed at 0.01 whatever the grid class. A native LevelSet gets
  `0.1*background/3` and an unclassified grid gets `0.0` (always 16 bit, or 1 bit for constant leaves). `quantize`
  is documented for fog (the K4.4/K4.16 callers), and `tolerance` is a parameter, so a caller can pass the
  native value. Not a size effect on the primitives (all fog).

from, which is the tell that it is slack, not precision.

## Recommendation

1. **Keep ours; no code change.** Default tolerance 0.01 already is native's (FogVolume) default, and our image
   is what a correct NanoVDB writer produces. Do not "match" the native size: that would mean writing 2.4 MB of
   dead bytes.
2. **Document it** (DIVERGES V30 below) and keep `tolerance` as the knob. Tighter tolerances are cheap on the
   tail: 0.001 costs +11% (sphere) / +18% (torus) / +0.5% (box) and cuts mean error 50×; the mean is already
   ~1e-4 at 0.01, so the default stays.
3. Optional (not now): a LevelSet-aware default (`0.1 * background / 3`) if `quantize` ever takes SDF input;
   today it is fog only.
4. Native-compat consequence for K4.17: a native FpN image read by us is fine; our smaller image read by native
   tools is fine (`mGridSize` is simply the true size).
5. Upstream: the double count could be reported to OpenVDB (`mLeafNodeSize` should be
   `getOffset(leafCount) - mCodec[0].offset`). Owner's call; not done here.
