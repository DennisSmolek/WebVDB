# Handoff: K4.1 — active tiles in the `.vdb` parser (`bunny_cloud.vdb`)

Gate item (PHASES K4, first): **`bunny_cloud.vdb` parses and round-trips through the CPU oracle: PASSED.**

## What changed

All in `packages/vdb/src/tools/**` and `packages/vdb/test/tools/**`.

- **Parser: active tiles** (`vdb/tree.ts`, `vdb/grid.ts`, `vdb/types.ts`, `vdb/parse.ts`). Root, upper and lower
  nodes may hold active tiles: a slot with its child bit clear and value bit set. They are now read (OpenVDB
  `RootNode::readTopology` / `InternalNode::readTopology`; from v222 one value per slot, before v222 one per
  child-off slot, packed) and exposed as `VdbGrid.iterTiles(): Iterable<VdbTile>` (`{ origin, dim: 8 | 128 |
  4096, value }`). `readValue` resolves leaf, then the enclosing active tile, then background.
  `activeVoxelCount` counts each tile as `dim^3`. The "active tile rejected" errors are gone. Inactive tiles are
  still dropped, as before.
- **Parser: Blosc** (`vdb/blosc.ts`, new, and `vdb/compression.ts`). This was needed for the gate. The
  openvdb.org `bunny_cloud.vdb` is **Blosc/LZ4-compressed** (OpenVDB 12.1, file version 223), so active tiles
  alone would not have parsed it. The new file is a pure-TS Blosc1 decoder: byte unshuffle, split and unsplit
  blocks, LZ4 and zlib codecs, memcpy'd frames. BloscLZ, Snappy, Zstd and bit-shuffle throw
  `VdbUnsupportedError`. It handles OpenVDB's zero padding of buffers under 48 bytes. It is written from the
  Blosc1/LZ4 format descriptions; no code was ported.
- **NanoVDB build** (`nanovdb/tree.ts`, `nanovdb/serialize.ts`, `nanovdb/stats.ts`, `nanovdb/build-from-vdb.ts`).
  - `buildFromLeavesDetailed(..., { tiles })` places active tiles as NanoVDB tiles; they are not expanded into
    leaves:
    - lower and upper tiles set the value-mask bit and the table value;
    - root tiles get `child = 0`, `state = 1` and the value, in a root table sorted by origin (OpenVDB's map
      order, which CreateNanoGrid copies).
  - TreeData `mTileCount[3]` and `mVoxelCount` (leaves plus `dim^3` per tile) are filled. `BuiltGrid` gains
    `tileCounts`.
  - Validation rejects tiles that overlap a child, misaligned tiles, unknown sizes and duplicates.
  - `buildFromVdb` passes `grid.iterTiles()` through.
- **Stats follow NanoVDB `tools/GridStats.h` exactly.** A tile adds its value with weight `ChildT::NUM_VALUES`:
  512 (lower), 4096 (upper), 32768 (root). That is the child's *slot* count, not its voxel count, and it is
  native's convention. The bbox grows by the tile's full extent.
- **Quantize** (`nanovdb/quantize.ts`). It now keeps source tiles as tiles instead of expanding them into
  constant leaves. This was the "trivially extendable" case: the serializer takes tiles now. It also removes the
  old throw on active root tiles.
  - Effect on the native primitives (`sphere`/`box`/`torus_fog_float` → fp8): our output is now **byte-size
    identical to native** (2,914,208 / 2,639,392 / 3,266,240 bytes), with identical node counts.
  - The FpN bit-width distribution now matches native exactly.
- **writeNvdb** copies TreeData tile counts into the file metadata (it used to write 0s).

- `test/tools/active-tiles.test.ts` (new, 16 tests, no assets). It uses `test/tools/synthetic-vdb.ts`, a tiny
  uncompressed `.vdb` writer, to build a tree with tiles at every level:
  - an active root tile, an upper tile, and two lower tiles (one at negative coords);
  - inactive tiles at each level, which must be dropped;
  - two leaves.

  - parse: tile list, voxel count, `readValue`;
  - build: TreeData tile counts, the root tile entry and its order, the root bbox, `readValue` and

  - fp8/fpn quantize keeps the tiles; writeNvdb metadata; validation errors.
- `test/tools/blosc.test.ts` (new, 8 tests). The LZ4 vector comes from the reference `lz4` CLI (an independent

- `test/tools/bunny-cloud.test.ts` (new, 5 tests, skipped without the asset). It checks:

  - 1000 trilinear samples (half of them straddling tile edges) against trilinear interpolation of the parsed
    tree;
  - result: 0 mismatches and max error 0.

## Open issues

1. **Half-float zero-count arrays (parse desync).** `bunny.vdb`, `icosahedron.vdb` and `fire.vdb` (OpenVDB 12.1,
   v223, half-float) fail with "i64 … exceeds safe integer range". The cause: current OpenVDB's
   `HalfWriter`/`HalfReader` return early when `count < 1`, so a node with no values to store writes no i64 at
   all. The v222 samples (sphere, cube, teapot) were written by an older writer that does write the i64 for zero
   counts. This is not tile-related and not needed for the gate. Options:
   - retry the grid with the other convention when the parse fails or the voxel count disagrees with
     `file_voxel_count`;
   - pick the convention by writer version, but the header's library version is unreliable (the old samples say
     "1.1").
   The test that settles it: all three files parse and match `file_voxel_count`.
   `explosion.vdb` now gets past Blosc and stops at `vec3s` (K4.2).
2. **Inactive values in compressed node arrays.** `compression.ts` defaults `inactiveVal0`/`inactiveVal1` to 0.
   OpenVDB defaults them to `background` (meta 0) or `-background` / `background` (other metas). This only
   changes *inactive* values inside leaves (level-set leaves read 0 instead of ±background at band edges, which
   trilinear sampling sees). Fog volumes (background 0) are unaffected. I left it alone because fixing it changes
   leaf payload bytes for the level-set samples and may move demo goldens.
3. Inactive tiles (for example a level set's interior −background tiles) are still dropped by the parser and
   written as background. That is unchanged behaviour.

## Hardening

Hostile-input pass over the pure-TS decompression path (`blosc.ts`, `inflate.ts`, `compression.ts`). Every
failure is a `VdbFormatError` raised before any allocation larger than the node's expected output.

- **S1 output cap.** `decompressBlosc(frame, { maxBytes, expectedCbytes })`. `compression.ts` passes
  `maxBytes = max(count * elementSize, 48)` and `expectedCbytes = numCompressedBytes`. Rejected before
  allocating: `nbytes > maxBytes`, `blocksize` zero or `> maxBytes`, `typesize` 0, `cbytes` outside
  `[16, frame.length]` or `!== expectedCbytes`, `16 + 4 * nblocks > cbytes`, memcpy'd frames where
  `cbytes !== nbytes + 16`, and the header flag bit `0x08`. Without `maxBytes` the cap defaults to 1 GiB.
- **S2.** Scratch buffer is `min(blocksize, nbytes)`, and `blocksize <= maxBytes`, so nothing allocates more than
  the output.
- **S3.** Block starts must satisfy `16 + 4 * nblocks <= bstart` and `bstart + 4 <= cbytes`. All stream reads are
  bounded by `cbytes`, not `frame.length`. Messages name the field.
- **S4.** `inflateZlib(data, maxOut)` / `inflateRaw(data, maxOut)` throw when output would pass `maxOut`
  (default 1 GiB). The Blosc zlib codec caps each stream at its split size; the zip path in `compression.ts` caps
  at `count * elementSize`. Dynamic-table parsing also rejects `hlit > 286`, `hdist > 30` and code-length
  repeats that overrun the table (previously silently truncated).
- **S5.** Split decision is c-blosc's `blosc_d` rule: split only if `!dont_split && typesize <= 16 &&
  bsize / typesize >= 128 && !leftover`. A block that does not divide into its splits is an error (upstream
  returns -1 too).
- **N7.** The `<= 0` raw sentinel must be a whole, non-negative number of elements and `<= count`. Also added:
  the decoded value count must equal the on-disk count, and zip/blosc payloads shorter than needed are a
  `VdbFormatError` instead of a `RangeError` from `DataView`.

Tests: `packages/vdb/test/tools/blosc-hostile.test.ts` (29 tests). Each hostile case asserts `VdbFormatError`,
under 200 ms, and (via a `Uint8Array` constructor spy) no allocation above the cap. Real-frame vectors come from
python-blosc 1.21 (c-blosc 1.21.x) in a throwaway venv: a split LZ4 frame (flags 0x21), a split zlib frame, a
typesize-24 frame (also decoded with the dont-split flag cleared, as pre-1.14 encoders wrote it), a memcpy'd
20-float frame. Hand-built flag-less 20-float and typesize-24 frames cover the legacy path.

Differences from the review's description of upstream c-blosc (`blosc.c`, 1.21): upstream rejects
`blocksize > destsize` and `blocksize <= 0`, not `blocksize > nbytes`; a single block larger than `nbytes` (the
leftover case) is accepted, and so is it here. The "pre-1.14 compatibility rule" is not a separate branch: the
`typesize <= 16 && bsize / typesize >= 128` clause in `blosc_d` is it, applied to every frame. Upstream does not
check block-start lower bounds (`>= 16 + 4 * nblocks`); that check is ours. `c-blosc` also checks
`src_offset > compressedsize - 4`, which we match.
